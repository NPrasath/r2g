# Training sequence

Run one cohort through the full lifecycle. Keep real artifacts and decisions in GitHub; the examples in this starter are deliberately unapproved and unexecuted.

| Lab | Main human owner | Team outcome | Guide |
| --- | --- | --- | --- |
| 00 | Technical Manager | Roles, access, first real CI evidence | [Foundation](labs/00-foundation.md) |
| 01 | Business Analyst + Tester | Business decisions and testable requirement | [Requirements](labs/01-requirements.md) |
| 02 | Developer + Technical Manager | Accepted design and bounded implementation issue | [Design and tasks](labs/02-design-and-tasks.md) |
| 03 | Tester / QA | Acceptance/regression plan and data | [Test design](labs/03-test-design.md) |
| 04 | Developer | Agent-assisted implementation and developer tests | [Implementation](labs/04-implementation.md) |
| 05 | Tester + Technical Manager | Independent review, defects, verified fixes | [Review and QA](labs/05-review-and-qa.md) |
| 06 | BA + Technical Manager | UAT and a traceable training release decision | [UAT and release](labs/06-uat-and-release.md) |
| 07 | All roles | Quality/effort retrospective and skill improvement | [AI evaluation](labs/07-ai-evaluation.md) |

Test planning starts in Lab 01 and runs alongside design and coding. The sequence identifies handoffs, not a rule that the Tester waits until development is complete.

The [backlog manifest](backlog.json) contains proposed issue titles, role owners, dependencies, and exercise instructions. It does not mean the issues have been created or assigned. The repo owner/facilitator can use it to seed the actual cohort backlog. Record real URLs after creating issues.

See [the facilitator guide](facilitator-guide.md) for pacing and evaluation. Repeat with a later R2G module once the team completes one full increment.
